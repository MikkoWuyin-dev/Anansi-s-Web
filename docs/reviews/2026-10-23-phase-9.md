# Phase 9 review — quality gates, 2026-10-23

The three-layer review MCD §10 asks for, run after the measurement and audit of
roadmap Phase 9. Numbers and methods are in
`docs/specs/0010-measured-quality.md`; this report judges the phase and records
what was found, how bad it is, and what happened to it.

Reviewed: the production build at 127.0.0.1:4175, desktop and 390 by 844
phone widths, in both modes, with keyboard input. Lighthouse 13, headless
Chromium. The whole `npm run verify` gate is green.

## Layer 1 — Plan alignment

**PASS, with one recorded miss.**

| Roadmap step | Deliverable | Result |
|---|---|---|
| 9.1 Performance | recorded measurements for every MCD §8 budget | six met; the mobile miss and its interaction cost accepted |
| 9.2 Accessibility audit | audit against MCD §9 and PRD §36 | one defect found and fixed; two commitments unobservable here |
| 9.3 Font and network decisions | a recorded decision on the external face | self-hosted, licence shipped, no third-party request remains |
| 9.4 Production review | this report | findings triaged below |

Nothing was built that the phase did not ask for. Three changes landed:

- The story's title became the page's `h1` (9.2's one fix).
- Space Grotesk moved from Google Fonts to `public/fonts/` (9.3).
- `public/robots.txt` was added so the SEO category's robots audit passes
  against a real host rather than a 404. That is measurement scaffolding, not a
  product change.

The 9.1 done-when line lists eight budgets. Six are met. The two misses share
one cause and one decision: Lighthouse mobile scores 69 to 73 against 75, and
mobile time-to-interactive is 4.5 to 5.7 s, above the 3.5 s
first-usable-interaction budget when the scene chunk is counted (the DOM is
interactive at 1.7 s without it). The owner decided on 2026-10-23 to keep the
world immediate and record both rather than defer the scene or drop it on
narrow screens.

## Layer 2 — System integrity

**PASS.**

- **Boundaries.** No engine, state, or world code changed in this phase.
  `src/engine/purity.test.ts` and `src/world/purity.test.ts` pass unchanged;
  the scene still receives its data as props and reads no storage.
- **Tokens.** The new `@font-face` carries no colour, and
  `src/app/tokens.test.ts` still finds every raw colour inside the two token
  blocks. The heading change is a tag change only: `.story__title` keeps its
  scale, weight, casing, and focus rule, so the visual system is untouched.
- **The mode authority.** Unchanged and verified live: Enter on the switch
  flips `<html data-mode>`, the switch's accessible name, and `theme-color`
  together.
- **The one fetch mode.** The preload uses `as="font"` with `crossorigin`,
  matching the CORS fetch the stylesheet makes. A mismatch here would download
  the file twice; the built page's network log shows one request.
- **The heading rule.** Every ritual state now has exactly one `h1`, and a new
  test fails if the story title drops back to `h2`. Hidden panel headings
  (`Your web`, day labels) stay out of the outline because the panel carries
  the `hidden` attribute.
- **Standards.** The markup stays presentational; no rule moved out of
  `ritual.ts` or `history.ts`; no new dependency; no stored shape changed.

## Layer 3 — Production readiness

**ISSUES FOUND, none blocking after disposition.**

### Findings

| # | Severity | Finding | Disposition |
|---|---|---|---|
| 1 | HIGH | Lighthouse mobile performance 69 to 73 against a target of 75 | **Accepted** by the owner on 2026-10-23: keep the world immediate, record the miss. Cause is the 238.81 kB lazy scene chunk's parse under four-times CPU throttling; with that chunk blocked the same page scores 99. |
| 2 | HIGH | First usable interaction 4.5 to 5.7 s with the scene counted, against 3.5 s | **Accepted** as the same cost as #1. The DOM is interactive at 1.7 s, and no ritual action waits on the scene, but main-thread blocking can delay a tap during the scene's parse. |
| 3 | MEDIUM | Focus rings and every reduced-motion branch were never observed, only tested | **Recorded as unverified.** The preview webview's page is never the focused window, so `:focus-visible` cannot match, and the reduced-motion media query cannot be emulated there. Styles, rules, and ring contrast are covered by tests. |
| 4 | LOW | The History control measures 39.9 px tall at 390 px, against the 44 px the mode switch uses | **Not changed.** No documented tap-target rule is violated and the control is comfortably wide. Follow-up in spec 0010. |
| 5 | LOW | After "Yes, mark it learned" the confirm block unmounts and focus falls to `body`; the next Tab starts at the browser chrome | **Not changed.** The live region carries the outcome and the day is over, so no action is stranded. An effect to return focus to the title would be the fix if it is ever reported. |
| 6 | INFO | Lighthouse desktop performance is exactly 85, the floor | **Noted.** Any regression on desktop now fails the budget; there is no headroom. |

### What holds

- No console messages or failed requests in the built page, in either mode.
- The font falls back to the system sans stack if the file is missing
  (`font-display: swap` plus the stack), and nothing else on the page depends on
  it.
- The scene failing still leaves the ritual intact: the error boundary and the
  DOM description are unchanged.
- The keyboard path completes a whole day without a pointer, and the history
  panel closes on Escape with focus returned to its control.

## What is not true

- Mobile Lighthouse does not meet its budget, by design of the accepted miss.
- The focus ring has not been seen with human eyes in this environment; it is
  known from CSS and from the contrast computation, not from a picture.
- Reduced motion has never been observed running, in any phase.
- The 3D transitions still have not been seen as pictures in this preview, so
  their quality is judged from code, tests, and descriptions.
- Frame time is a CPU submission figure, not a GPU timer.

## Verdict

Phase 9 is complete. Every budget is measured, the one miss is caused, owned,
and accepted rather than hidden, the accessibility audit found one real defect
and it is fixed, and the last third-party request is gone. What remains
unverified is named above and carried into the next phase.

Ready for Phase 10: hardening and deployment.
